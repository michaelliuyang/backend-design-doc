# 研发视角统一评分标准

本文件定义 `lanhu-skill` 在需求/原型/设计稿分析场景下统一使用的研发评审评分标准。
AI 在输出评分结论时 **必须逐条检查** 本文件中的所有要求，并使用固定字段、固定顺序、固定等级。

---

## 1. 适用范围

统一评分表适用于以下分析主体：
- PRD / 原型页面分析（`analyze-pages`）
- UI 设计稿分析（`analyze-designs`）
- 需求澄清、开发视角、测试视角、后端设计、接口设计等派生分析模式

以下工具型流程不单独输出完整评分表，仅作为补充证据来源：
- `get-design-slices`
- `get-members`
- `say-*`
- `resolve-invite`

---

## 2. 输出原则

- 评分必须建立在**已提取的页面/设计/规则/接口证据**之上，不得凭空打分。
- 评分必须区分：
  - **事实**：页面上明确存在的内容、文档原文、设计稿显式表现
  - **推断**：基于事实做出的研发判断
- 所有分析模式必须输出**同一张评分表**，不得因模式不同而改变字段结构。
- 评分表字段顺序必须固定，不得随机省略。
- 若证据不足，应在 `missing_evidence` 和 `blocking_questions` 中明确说明，不得用主观臆测补齐。

---

## 3. 总评分结构

最终评分结论必须先输出一张总评表，字段固定如下：

| 字段 | 含义 |
|------|------|
| `review_scope` | 本次评审范围（模块/页面/设计图/文档） |
| `artifact_type` | `prd` / `prototype` / `design` / `mixed` / `other` |
| `analysis_mode` | 当前分析模式 |
| `overall_score` | 总分（0-100） |
| `overall_grade` | 总体等级（A/B/C/D/E） |
| `release_readiness` | 可进入下一阶段的判断 |
| `decision` | `通过` / `有条件通过` / `需补充后复评` / `阻塞` |
| `summary` | 一句话总结 |
| `top_risks` | 前 3-5 个主要风险 |
| `blocking_questions` | 阻塞性待确认项 |
| `evidence_basis` | 评分依据（页面/设计图/规则/接口等） |

---

## 4. 固定评分维度与权重

统一使用以下 6 个维度：

| 维度 | 权重 | 说明 |
|------|------:|------|
| `clarity_and_completeness` | 25 | 需求表达是否清晰、是否缺关键页面/字段/状态/边界 |
| `interaction_and_flow_integrity` | 15 | 页面、流程、状态流转是否闭环 |
| `rule_and_validation_explicitness` | 15 | 业务规则、校验规则、异常规则是否明确 |
| `engineering_implementability` | 20 | 是否足以支撑研发做接口、状态、数据结构设计 |
| `cross_artifact_consistency` | 15 | 文档、页面、设计稿、接口规则之间是否一致 |
| `risk_and_dependency_control` | 10 | 风险、依赖、灰区、待确认项是否被识别 |

总分 = 所有维度加权总和，满分 100。

---

## 5. 分项评分固定字段

每个维度必须输出同一组字段：

| 字段 | 含义 |
|------|------|
| `dimension` | 维度名 |
| `score` | 该维度分数 |
| `grade` | 该维度等级 |
| `weight` | 权重 |
| `verdict` | `通过` / `部分通过` / `不通过` |
| `strengths` | 已明确、做得好的地方 |
| `issues` | 发现的问题 |
| `missing_evidence` | 当前缺失的证据或输入 |
| `impact` | 对研发的影响 |
| `recommendations` | 建议补充或修复的内容 |

---

## 6. 等级与决策映射

### 6.1 总体等级

| 等级 | 分数区间 | 含义 |
|------|----------|------|
| A | 90-100 | 信息充分、规则明确，可直接进入研发设计/拆解 |
| B | 80-89 | 有少量缺口，不影响主流程，可带条件推进 |
| C | 70-79 | 存在明显缺项，需要补充后再进入详细设计 |
| D | 60-69 | 关键闭环或约束不清，研发风险较高 |
| E | 0-59 | 阻塞项明显，不宜进入开发 |

### 6.2 决策映射

| 等级 | 决策 |
|------|------|
| A | 通过 |
| B | 有条件通过 |
| C | 需补充后复评 |
| D | 阻塞 |
| E | 阻塞 |

### 6.3 release_readiness 建议文案

| 情况 | 建议文案 |
|------|----------|
| A/B 且无阻塞项 | 可进入研发设计 / 可进入任务拆解 |
| B 有少量待确认 | 可带条件进入研发设计 |
| C | 需先补充规则后再进入详细设计 |
| D/E | 不可进入开发，需先完成需求澄清 |

---

## 7. 扣分规则

### 7.1 阻塞级问题
出现任一项，总评不得高于 C；严重时直接降为 D / E：
- 核心对象边界不清晰
- 核心主流程缺失或无法闭环
- 关键状态流转未定义
- 关键字段/必填规则/提交条件未定义
- 成功/失败反馈未体现
- 文档与设计稿存在明显冲突
- API / 后端设计依赖 DDL 或字段映射，但输入缺失

### 7.2 中度问题
每项建议扣 5-10 分：
- 页面链路不完整（列表/详情/新增/编辑/提交未闭环）
- 异常场景未覆盖
- 文案有描述但缺执行规则
- 设计稿体现了页面，但缺状态/空态/错误态
- 接口/后端设计无法稳定映射到页面动作

### 7.3 轻度问题
每项建议扣 1-4 分：
- 命名不一致
- 局部交互文案不清晰
- 权限、空态、边界场景说明不足
- 统计口径未完全写清

---

## 8. 证据与覆盖要求

评分前必须先完成以下证据提取：
- 能力点 / 页面要点列表
- 规则提取（业务规则 / 校验规则 / 状态规则）
- 关键流程或状态流转
- 待确认项和明显冲突

建议在评分前输出轻量覆盖矩阵：

| 能力点 / 页面要点 | 当前证据覆盖情况 | 结论 |
|------------------|------------------|------|
| XX功能 | 页面+文案已体现 | 已覆盖 |
| XX异常流程 | 仅文案提到，页面未体现 | 部分覆盖 |
| XX状态流转 | 未找到明确证据 | 未覆盖 |

评分时必须引用该覆盖结论，不得脱离证据独立打分。

---

## 9. 一致性检查要求

评分时必须检查以下一致性：
- 页面文案与流程是否一致
- 设计稿与交互语义是否一致
- 字段/状态/动作命名是否一致
- 规则说明与页面行为是否一致
- 接口设计约束与业务动作是否一致

若发现冲突：
- 必须写入 `issues`
- 必须体现在 `cross_artifact_consistency` 维度扣分
- 必须列入 `blocking_questions` 或 `top_risks`

---

## 10. 各模式下的额外关注点

统一评分表不变，但不同模式需要额外关注不同证据：

### developer
- 能否直接支撑页面开发、接口对接、状态流转实现

### tester
- 是否足以编写正向/异常/边界测试用例

### explorer
- 是否足够支持范围评审、依赖识别、行动项梳理

### clarifier
- 是否明确指出规则缺失、逻辑矛盾、边界未定义

### backend_designer
- 是否足以落到 Service、状态机、流程图、DDL

### api_designer
- 是否所有参数都能回溯到 DDL 字段
- 是否遵守 `references/api-design-rules.md`
- 是否接口粒度合理且可合并去重

---

最终输出时，统一评分表必须按以下顺序出现：

1. `## 📊 研发评审统一评分表`
2. 总评表
3. 分项评分表（6 个维度，顺序固定）
4. `## 🚫 阻塞项`

## 12. 严禁事项

- 禁止只给一个总分，不解释证据来源。
- 禁止不同模式使用不同评分字段结构。
- 禁止为了迎合用户而虚高打分。
- 禁止在证据不足时假设规则已存在。
- 禁止把“设计美观度”当作研发评分核心依据；设计稿评分重点是**研发可落地性**。
