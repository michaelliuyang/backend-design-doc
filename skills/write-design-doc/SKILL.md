# 写后端详细设计文档

## 目标

产出一份可评审、可落地、可直接作为 AI Coding 输入的后端详细设计文档。文档必须把产品意图或概要设计思路转成明确的后端边界、数据模型、API 契约、处理流程、异常处理、实施任务和验收标准。

## 兼容与加载约定

- 本 Skill 位于多 Skill 仓库的 `skills/write-design-doc/` 目录。
- 本 Skill 不依赖 Codex 专有工具；Claude Code、Codex 或其他支持 Agent Skills 的工具都应按本文和 `references/` 执行。
- `agents/openai.yaml` 仅作为 Codex UI 元数据；执行规则以 `SKILL.md` 和 `references/` 为准。
- 除非用户明确要求，不要创建 Codex-only 或 Claude-only 的输出格式。

## 工作流程

1. 先读取用户提供的需求分析、PRD、原型说明、现有代码、DDL、API 文档和概要设计思路，再开始写文档。
2. 识别材料中的事实源。若产品材料与技术文档或表结构冲突，明确写出冲突，并优先选择技术上更安全、可实现的基线，不要静默拼接矛盾信息。
3. 提取功能范围、非目标范围、参与角色、租户/用户上下文、权限要求、集成点和数据生命周期。
4. 如涉及表设计，先读取 `references/table-design-validation-rules.md`，并在最终 DDL 前执行其中的门禁规则。
5. 如涉及 API 设计，先读取 `references/api-rules.md`，再生成接口列表、请求对象和响应对象。
6. 如涉及业务异常或失败分支，先读取 `references/error-codes.md`，再分配错误码。
7. 使用 `references/backend-design-template.md` 作为输出结构。只有在章节确实无关时才裁剪，不要保留空占位。
8. 结尾必须包含 AI Coding 交接内容：实施任务、已知目标模块/文件、测试用例、兼容风险和待确认决策。

## 输出要求

- 默认输出完整 Markdown 文档，不只给建议摘要；除非用户明确只要分析。
- 优先使用明确规则、表格、Mermaid 图、请求/响应示例，不写泛泛的架构描述。
- 保持方案可实现：除非需求确实需要，不新增平台、层级、依赖、异步机制或通用抽象。
- 当本地材料体现了既有服务边界、命名规范、响应包装、租户模型和审计字段时，必须沿用。
- 显式标注假设，不要把缺失的产品规则包装成确定结论。
- 将未解决的产品或工程问题放到最终的 `待确认事项` 章节，并写清影响和建议默认值。
- 当源材料或用户请求是中文时，面向用户的设计文档必须使用中文。

## 交付前门禁

交付前检查：

- 每个范围内需求都已映射到后端行为、API、表变更、现有能力复用或明确的非后端处理。
- 每条写路径都说明了幂等性、事务边界、校验规则和必要的审计字段。
- 每个跨服务调用都说明了调用方、被调用方、协议、失败处理，以及是否降级或重试。
- 每张新增或变更表都说明了用途、关键字段、索引，以及与 API 对象的关系。
- 每个 API 都包含方法、路径、分类、鉴权/租户/用户上下文、请求对象、响应对象、校验规则和主要错误分支。
- 文档中不得残留 `TODO`、`TBD`、`xxx`、空代码块或模板占位话术。
- 模板中的空表格、示例 JSON、示例 Mermaid 或示例伪代码必须被真实内容替换；无关章节直接删除。

## 引用资料加载规则

- 起草完整设计文档时，读取 `references/backend-design-template.md`。
- 设计或评审 API 前，读取 `references/api-rules.md`。
- 设计或评审 DDL、索引、API/DDL 字段映射前，读取 `references/table-design-validation-rules.md`。
- 设计业务异常处理前，读取 `references/error-codes.md`。
